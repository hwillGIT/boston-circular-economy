# Architectural Implementation Options: Flow A (Toaster/Small Appliances) & Flow B (Shirt/Textiles)

> **Target Application**: Boston Circular Economy Platform  
> **Prepared By**: Subagent 3 (Multi-Option Product Strategist)  
> **Target Repository**: `codeforboston/boston-circular-economy`  
> **Reference Prototype**: `circular-economy-prototype.vercel.app`

---

## Executive Summary

Based on a thorough review of `docs/customer_journey_and_agentic_team_design.md` and the existing codebase in `client/src/`, `server/src/`, and `etl/`, I have formulated **3 distinct architectural implementation options** for bringing **Flow A (Toaster/Small Appliances)** and **Flow B (Shirt/Textiles)** into the production platform. 

Each option addresses the needs of our target persona (*Jordan*, the carless Boston resident reliant on MBTA transit) while providing concrete strategies for UI component design, state management, GeoJSON spatial filtering, and technical trade-offs.

---

## Architectural Implementation Options

### Option 1: Static Client-Driven Flow Architecture (Lightweight SPA)

#### 1. Overview
Option 1 is a pure frontend approach. The React client loads pre-merged static GeoJSON datasets generated by the Python ETL pipeline (`etl/merge_processor.py`). Routing, filtering, and decision-tree stepping take place entirely in the browser.

#### 2. UI Component Structure (`client/src/`)
```
client/src/
├── routes/
│   ├── flow/
│   │   ├── index.tsx                # Journey entry (Select Appliance vs. Textile)
│   │   ├── toaster.tsx              # Flow A: Small Appliance Journey Page
│   │   └── shirt.tsx                # Flow B: Textile/Clothing Journey Page
├── components/
│   ├── flow/
│   │   ├── FlowStepWizard.tsx       # Decision step container (Problem -> Mobility -> Recommendation)
│   │   ├── PathOptionCard.tsx       # Cards for Path A1/A2 or Path B1/B2/B3 with cost & transit badges
│   │   └── ImpactBadge.tsx          # Waste diversion metric badge (e.g. "Saves 2.5 lbs E-Waste")
│   ├── map/
│   │   ├── StaticLeafletMap.tsx     # MapLibre/Leaflet rendering pre-loaded GeoJSON features
│   │   └── TransitFilterBar.tsx     # Filter UI by MBTA Line (Orange, Red, Green) & Walk Time
```

#### 3. State Management
* **URL Search Params**: Managed via TanStack Router (`useSearch()`). Encodes selected options (`?flow=toaster&path=clinic&mbta=orange&maxWalk=10`) making journeys shareable and bookmarkable.
* **Component Context**: Lightweight React Context (`FlowContext`) to track step index (Step 1: Diagnose -> Step 2: Transit -> Step 3: Action).

#### 4. GeoJSON Data Filtering
* **In-Memory JS Filtering**: Loaded GeoJSON features (`boston_repair_locations.geojson`) filtered in-browser using standard array operations or Turf.js:
  ```typescript
  const filteredFeatures = geojson.features.filter((feature) => {
    const matchesCategory = feature.properties.category === 'small_appliance';
    const matchesTransit = selectedMBTALine 
      ? feature.properties.mbta_lines.includes(selectedMBTALine) 
      : true;
    const matchesCost = filterFreeOnly ? feature.properties.cost_type === 'free' : true;
    return matchesCategory && matchesTransit && matchesCost;
  });
  ```

#### 5. Pros & Cons
* **Pros**:
  * Zero backend server overhead or database hosting cost.
  * Instant filter updates and lightning-fast user interactions.
  * Simple deployment to static hosts (Vercel, GitHub Pages).
* **Cons**:
  * Static GeoJSON files become outdated when community Fix-It Clinics or Clothing Swaps change schedules.
  * Cannot support community submissions or dynamic user-contributed locations without rebuilding static assets.

### Option 2: Modular Full-Stack REST & Portal Architecture (Full-Stack Portal)

#### 1. Overview
Option 2 connects the React frontend (`client/src`) to the Express backend (`server/src`). The backend queries a database (SQLite with SpatiaLite or PostgreSQL/PostGIS) populated by ETL merged outputs, serving dynamically filtered GeoJSON API responses and accepting community event submissions.

#### 2. UI Component Structure (`client/src/`)
```
client/src/
├── routes/
│   ├── flow/
│   │   ├── $category.tsx            # Dynamic route for /flow/toaster, /flow/shirt
│   │   └── submit-event.tsx         # Community submission form for Fix-It Clinics / Swaps
├── components/
│   ├── flow/
│   │   ├── DynamicFlowContainer.tsx # Wizard driven by backend category config
│   │   ├── PathComparisonGrid.tsx   # Grid comparing Professional vs. Community Skill-Share
│   │   └── EventScheduleList.tsx    # Dynamic list of upcoming community mending/repair events
│   ├── filters/
│   │   ├── SpatialFilterDrawer.tsx  # Drawer with transit line multi-select & walk radius sliders
│   ├── map/
│   │   └── VectorMapView.tsx        # Map showing shop locations + MBTA transit buffer overlays
```

#### 3. State Management
* **TanStack Query (React Query)**: Caching and fetching server states for locations and events:
  ```typescript
  const { data: locations, isLoading } = useQuery({
    queryKey: ['locations', category, mbtaLine, maxWalkMinutes],
    queryFn: () => fetchLocationsAPI({ category, mbtaLine, maxWalkMinutes }),
  });
  ```
* **TanStack Router**: Manages active route states and syncs query parameters with `useQuery`.
* **Zustand**: Handles local UI state (drawer open/closed, highlighted map pin ID).

#### 4. GeoJSON Data Filtering
* **Backend Endpoint (`GET /api/v1/locations`)**: Express route runs spatial queries or SQL filter queries and returns a GeoJSON `FeatureCollection`:
  ```sql
  SELECT json_build_object(
    'type', 'FeatureCollection',
    'features', json_agg(ST_AsGeoJSON(l.*)::json)
  )
  FROM locations l
  WHERE l.category = $1 
    AND ($2::text IS NULL OR $2 = ANY(l.mbta_lines))
    AND ($3::numeric IS NULL OR l.walk_distance_meters <= $3);
  ```

#### 5. Pros & Cons
* **Pros**:
  * Dynamic data updates: Fix-It Clinics and Clothing Swaps can be updated in real time via API.
  * Enables community event submission and verification workflows.
  * Standardized production architecture with clean separation of ETL, DB, API, and Client.
* **Cons**:
  * Requires database setup (SQLite/SpatiaLite or PostgreSQL/PostGIS) and deployment infrastructure.
  * Adds small network latency for backend API calls (mitigated by TanStack Query caching).

### Option 3: Event-Driven City 311 & MBTA GTFS Integrated Platform (Enterprise / City Integrated)

#### 1. Overview
Option 3 targets deep integration with the City of Boston's municipal infrastructure. It combines real-time MBTA GTFS schedule feeds with waste diversion reporting APIs, providing live transit arrival times and reporting waste reduction metrics directly to City analytics dashboards.

#### 2. UI Component Structure (`client/src/`)
```
client/src/
├── routes/
│   ├── flow/
│   │   ├── $category/
│   │   │   ├── index.tsx            # Journey selector with live MBTA status indicator
│   │   │   └── $pathId.tsx          # Granular path detail page with real-time routing
├── components/
│   ├── transit/
│   │   ├── LiveMBTATracker.tsx      # Real-time arrival countdowns at nearest T stations
│   │   └── WalkshedPolyMap.tsx      # Map displaying 5/10/15 min walk buffers from T stops
│   ├── analytics/
│   │   └── CityImpactWidget.tsx     # Real-time municipal diversion metrics (tons saved by ZIP)
```

#### 3. State Management
* **TanStack Query + WebSockets / SSE**: Real-time push updates for live MBTA train arrivals and event seating capacity.
* **Global Telemetry Store (Zustand)**: Aggregates anonymous journey choices (e.g. "Jordan chose Repair Cafe over Landfill") to send impact telemetry to backend reporting endpoints.

#### 4. GeoJSON Data Filtering
* **Tile Server (Mapbox Vector Tiles / MVT)**: Backend serves pre-calculated vector tiles (`pg_tileserv` or `Martin`) for MBTA line buffers, station entrances, and repair spots.
* **Spatial Buffer Intersects**: Server performs ST_DWithin spatial buffer computations to filter repair locations strictly within a specified transit walk-shed.

#### 5. Pros & Cons
* **Pros**:
  * Real-time transit navigation gives Jordan instant transit confidence ("Next Orange Line train in 3 mins").
  * Direct alignment with City of Boston Year-1 waste diversion reporting and 311 integration.
* **Cons**:
  * High implementation complexity and ongoing operational/maintenance cost.
  * Dependency on external third-party uptime (MBTA GTFS feed and City APIs).

## Recommended Strategy & Phased Roadmap

I recommend adopting **Option 2 (Full-Stack Portal)** as the core architectural target for the platform, executed in a **2-Phase Hybrid Strategy**:

### Phase 1: MVP Frontend Fast-Track (Option 1 Pattern)
* Build `client/src/routes/flow/toaster.tsx` and `client/src/routes/flow/shirt.tsx` using TanStack Router.
* Consume pre-merged static GeoJSON generated by `etl/merge_processor.py` for immediate prototype parity.
* Implement MBTA transit line and cost filter controls in React.

### Phase 2: Backend Integration & Dynamic Events (Option 2 Expansion)
* Connect front-end TanStack Query hooks to Express API routes in `server/src/`.
* Enable community organizers to submit upcoming Fix-It Clinics (Path A2) and Clothing Swaps (Path B3).
* Store locations in SQLite/PostGIS database, serving dynamic GeoJSON FeatureCollections.
